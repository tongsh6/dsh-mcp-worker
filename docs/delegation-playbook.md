# 委派粒度手册：让 DSH 多干活、leader 少花 token

> 目标：Codex/ChatGPT、Claude Code 只做「定目标 + 验收」，把可独立验收的工作单元整体交给 DSH；
> 避免把活拆得太细，导致 leader 反复思考、反复调用工具，反而更慢、更贵。

---

## 1. 为什么微任务反而慢

每多一个 DSH 任务，leader 至少多付：

1. 一次 `dsh_run` 工具调用 + 任务描述生成；
2. 若干次 `dsh_status` 轮询（受客户端超时限制，通常 25–120s 一次）；
3. 一次 `dsh_result` 读取 + 结果判断；
4. 中间的思考 token（拆步骤、判断边界、串行编排）。

所以「改 1 个文件 = 1 个 dsh 任务」的粒度下，leader 的编排成本可能超过它省下的执行成本。

**判断阈值**：如果一件事预计少于 3 次工具调用、或 2 分钟内能做完，leader 自己做，别委派、更别拆成多个任务。

---

## 2. 粒度策略

一个 `dsh_run` = 一个**可独立验收的工作单元**，默认覆盖：

```
定位 → 实现/修改 → 自测 → 证据汇总
```

典型粒度：
- 一个功能点（含相关接口、页面、测试）；
- 一个 bug 修复（定位 + 改代码 + 回归测试）；
- 一个测试修复批次（一组相关失败用例）；
- 一次跨文件重构。

**只允许三种拆分**：
1. 彼此独立、可并行 → 一次 `dsh_batch_run` 发多个（不是串行小任务）；
2. 需要用户/leader 做决策（如方案选型、权限申请）；
3. 风险隔离（先小范围验证，再扩大）。

---

## 3. 任务模板（dsh_run 的 task 字段）

```text
[目标] 一句话目标 + 为什么（验收依据）
[入口/上下文] 关键文件、复现步骤、已知约束
[范围] 可改：...；不可改：...
[验收] 运行 <命令>，期望 <结果>；失败附完整输出
[证据] 变更文件清单 + 测试结果 + 风险点
[预算] 预计 <5–30> 分钟；超时用 <值>
```

给**目标与约束**，不要给逐步操作清单——DSH 会自己规划多步工具调用。

### 反例（太细，leader 成本高）

```
先读 a.ts，把第 12 行改成 X。
```
→ 下一个任务：「再读 b.ts，把 import 改掉」……leader 变成调度器。

### 正例（整体外包）

```
[目标] 修复订单页取消后仍收到站内消息的问题：运营取消整场活动后，不应再触发订阅通知。
[入口] 散客 fit-event、团队 group-event-management、门店 store-themed-activities 三个事件入口。
[范围] 可改：事件状态判定与通知触发；不可改：消息模板与推送通道。
[验收] 运行 <测试命令>，覆盖「取消后不发送」；失败附完整输出。
[证据] 变更文件 + 测试结果 + 风险点（是否有历史消息补发）。
[预算] 预计 20 分钟。
```

---

## 4. 交互模式（leader 侧）

```
dsh_run(task=模板, cwd=项目绝对路径)     # 只提交一次
  → dsh_status(task_id, wait_s=60~120)   # 长轮询，等到终态
  → dsh_result(task_id)                  # 取结果，审阅 diff / 测试证据 / 风险
```

- **不要** 5–25 秒高频轮询；worker 单次长轮询上限 `DSH_MCP_STATUS_WAIT_MAX_S`（默认 120s）；
- DSH 执行期间 leader 不要做同一件事（不要自己再读一遍代码「验证」）；
- 同一工作单元需要返工 → 用原 `session_id` 续聊，不要新建孤立任务；
- 并行：多个**独立**工作单元用 `dsh_batch_run` 一次发。

---

## 5. leader 的验收动作（只做这些）

1. 看 `dsh_result`：changed files / 测试命令与结果 / 风险点；
2. 抽查关键 diff（不要逐文件重读）；
3. 决定：通过 / 一次返工（session 续聊）/ 回滚；
4. 失败时把 `error` 原样反馈，不包装成完成。

---

## 6. 怎么验证策略生效

```powershell
# 对比改规则前后：leader 会话里 dsh 调用次数、leader token、时长
node scripts/leader-usage.mjs --since-hours 24
```

关注「强模型注意力」四个数：
- 每个工作单元的 **dsh 调用次数**（理想：1 次 submit + 1–2 次 status/result）；
- **Astra 介入次数**（提交 + 验收共 1–2 次；返工只允许一次）；
- Astra 花在**机械执行**上的工具调用/轮次是否下降（读文件、跑命令、逐轮改错）；
- leader token（input/output/cache_write）与总时长不上升。
- **总时长**不上升（DSH 执行时间归 DSH，leader 不重复劳动）。

也可用 `pnpm measure:ab` 跑同任务对照（leader 自己做 vs 委派）。

## 7. 与 Codex 原生子智能体的边界（重要）

Codex 桌面/CLI 自带 multi-agent（`spawn_agent` / `wait_agent` / `followup_task`）。**子智能体是独立子线程，工具集里没有 dsh MCP 工具**（只有 exec/send_message 等），所以：

- 主线程把「需要多轮工具调用/改文件/跑测试」的工作交给子智能体 = 用贵的 leader 模型重复劳动，且永远用不上 DSH；
- 本次核查记录：主线程确实调用了 dsh（3×run、25×status、1×result、2×cancel），而最新 15:52 的 rollout 是**子线程**，0 次 dsh 调用——看起来就像「没用 dsh、在用子智能体」；
- 规则：**重活禁止交给原生子智能体**，由主线程 `dsh_run` 委派；子智能体只用于只读调研、单文件小改、与主线程并行且工具调用很少的活；子智能体发现需要重活时回报主线程。

- 全局规则：`~/AGENTS.md`（Claude Code 通过 `~/.claude/CLAUDE.md` 引用）与 `~/.codex/AGENTS.md`——已写入本策略；

## 9. 决策/执行分离（Astra 定位，核心）

> 目标不是「省钱外包」，而是**按能力分工**：Astra 等强模型只做判断与验收；执行/迭代交给 DSH。

| 角色 | 该做 | 不该做 |
|---|---|---|
| Astra（leader） | 定目标、业务语义、方案权衡、根因判断、验收标准、最终审阅 | 机械读文件、逐轮跑命令、反复试错、替 DSH 执行 |
| DSH（worker） | 定位、改文件、跑测试、机械重构、批量核对、整理证据 | 改业务决策、猜需求、越权改权限/ACL |

委派判断：**不是看任务大小，而是看是否需要强模型判断**。

- 执行密集但无需强判断 → 直接交 DSH（哪怕不大）；
- 需要强判断 → Astra 先做决策，再把「已确定」的执行段外包；
- 任务里写清 `[已定决策]`（DSH 不得改变）与 `[待你判断]`（遇到分支停下汇报）。

验收只看四样：变更文件、测试结果、风险点、需要 Astra 决策的点。
